# 5.3 使用 ob-operator 进行运维

ob-operator 是一款基于 Kubernetes Operator 框架构建的工具，用于在 Kubernetes 中管理 OceanBase 集群。它提供了一种简单可靠的方式来实现 OceanBase 集群的容器化部署，可以简化 OceanBase 集群的运维。ob-operator 定义了 OceanBase 数据库相关的各种资源并且实现相应的调协逻辑，因此用户可以像管理 Kubernetes 的原生资源一样，通过声明式的方式管理 OceanBase 集群。

当前 ob-operator 最新版本已支持通过 Dashboard 提供给用户管理 K8s 中的 OceanBase 集群的界面，调用 K8s 的 API 来实现 OceanBase 集群的资源管理，包括基础概览、创建集群、创建租户、监控指标、备份恢复、集群升级、集群扩缩容等，目前仅支持社区版 OceanBase 数据库镜像。

本文仅介绍通过配置文件实现部分核心运维操作时的注意事项，完整运维文档可参见官网 [OceanBase K8s 运维工具](https://www.oceanbase.com/docs/ob-operator-doc) 文档。

## 新建用户租户

通过 ob-operator 新建用户租户前，您需了解如下内容：

* 请确保 ob-operator 在 V2.0.0 或以上版本，建议使用最新版本。

* 创建租户前需保证 OceanBase 集群可正常运行使用。

* 用户租户事务日志盘资源建议为租户内存的 3~4 倍，用户租户内存不能小于 `__min_full_resource_pool_memory` 参数，可使用 root 用户登录 OceanBase 集群的 sys 租户，执行如下命令查看 `__min_full_resource_pool_memory` 参数。
  
  ```sql
  select * from oceanbase.GV$OB_PARAMETERS where name ='__min_full_resource_pool_memory';
  ```

* 若配置文件未指定 `spec.credentials.root` 字段中的 `secret` 内容，则新建完成的用户租户 root 用户密码默认为空，建议登录用户租户进行密码修改。

* 创建租户后，建议使用 root 用户登录 OceanBase 集群的用户租户，执行 SQL 命令创建用户租户下的普通用户。

使用 ob-operator 新建用户租户的详细操作可参见官网《OceanBase K8s 运维工具》文档 [使用指南/租户管理/创建租户](https://www.oceanbase.com/docs/community-ob-operator-doc-1000000000659342)。

## 数据恢复

数据恢复依赖关键资源 OBTenant 和 OBTenantRestore，分别表示租户和租户恢复任务。因数据恢复行为的最终结果是产生一个新的租户，所以使用在 OBTenant Spec 中配置的 Source 字段来指定租户的恢复源。在租户资源中指定了数据恢复相关的字段之后，Operator 会创建出 OBTenantRestore 资源来执行具体的恢复任务。
<!-- 详细说明一下，现在的说明少了很多内容，比如什么叫 OBTenant Spec 中 -->

使用 ob-operator 进行数据恢复前，您需了解如下内容：

* 建议确保数据恢复的目标集群和源集群数据库版本保持一致。

* 需确保目标集群状态正常，可正常使用，并且目标集群剩余资源足够恢复租户，特别是数据磁盘空间。

* OceanBase 数据库当前仅支持将低版本的备份数据恢复到同版本或高版本中，但不支持将 OceanBase 数据库 V3.x 的备份数据恢复到 OceanBase 数据库 V4.x 版本，也不支持将 OceanBase 数据库 V4.0.x 的备份数据恢复到 OceanBase 数据库 V4.1.x 及以上版本。

* 可以通过配置文件 `tenantRole：STANDBY/PRIMARY` 参数配置是否将数据恢复成备租户，不设置默认恢复成主租户，即独立租户，恢复完成后不会和源租户再进行数据同步。

* 如果恢复源为 NFS 类型，需要确定挂载到 OceanBase 集群的备份 Volume 可用，且目标集群可以正常访问并有读写权限。

使用 ob-operator 进行数据恢复的具体操作可参见官网《OceanBase K8s 运维工具》文档 [使用指南/高可用/数据恢复](https://www.oceanbase.com/docs/community-ob-operator-doc-1000000000659355)。

## 集群扩容

### 横向扩容集群

[使用 ob-operator 横向扩容集群](https://www.oceanbase.com/docs/community-ob-operator-doc-1000000000659364)

可通过修改原部署集群的配置文件，在配置文件中添加新的 Zone 节点，实现集群横向扩容，从而增加租户副本数量。
<!-- 租户的副本是和 Zone 相关的，而不是和 OBServer 相关的对么 -->
使用 ob-operator 横向扩容集群前，您需了解如下内容：

* 扩容前需确保 OceanBase 集群处于 `running` 状态。

* 扩容前需确保服务器拥有足够的资源，能够支持新增 Zone 所需资源。

* ob-operator 会根据 OceanBase 数据库部署配置文件中的 nodeSelector 来决定 OBServer 节点的分布，如果需要指定节点可以配置 Kubernetes 的 node 节点配置 label，否则由 K8s 自动选节点。具体操作可参考 在[集群创建](https://www.oceanbase.com/docs/community-ob-operator-doc-1000000000659352)。
  <!-- 是要参考这个链接中的哪一块内容啊，没有看懂参考它干啥 -->

* 扩容完成后并不会自动为租户添加副本，需要手动为租户添加副本，详细操作可参见官网《OceanBase K8s 运维工具》文档 [使用指南/租户管理/修改租户/副本管理](https://www.oceanbase.com/docs/community-ob-operator-doc-1000000000659361)。

* 扩容完成后，如果 primary Zone 是顺序优先级策略，不能增加集群计算性能。如果 primary Zone 是随机策略，一般对分区表的性能是有一些影响的，具体需要看业务使用场景。例如：对分区表而言扩容后分区会打散到更多节点，每个节点分区数减少，计算速度提升，但跨了更多个节点数可能增加网络IO等。

### 纵向扩容集群
<!-- 跳转链接中也就只有三步，需要跳转到对应文档么，是否可以直接在这里写出来，省了用户的一次跳转 -->
[使用 ob-operator 纵向扩容集群](https://www.oceanbase.com/docs/community-ob-operator-doc-1000000000659365)

可通过修改原部署集群的配置文件，在原 Zone 中添加新的 OBServer 节点，实现集群纵向扩容，从而可以增加租户资源占用，提升租户业务性能和集群存储上限。

使用 ob-operator 纵向扩容集群前，您需了解如下内容：

* 扩容前需确保 OceanBase 集群处于 `running` 状态。

* 扩容前需确保服务器拥有足够的资源，能够支持新增 OBServer 节点所需资源。

* ob-operator 会根据 OceanBase 数据库部署配置文件中的 nodeSelector 来决定 OBServer 节点的分布，如果需要指定节点可以配置 Kubernetes 的 node 节点配置 label，否则由 K8s 自动选节点。具体操作可参考 在[集群创建](https://www.oceanbase.com/docs/community-ob-operator-doc-1000000000659352)。

* 扩容前，部署配置文件调整 `topology`下各个 Zone 的 replica 个数即可，建议保持一致。

* 扩容完成后，租户的数据不会自动均衡到新节点，需要手动修改资源池 Unit num，才会在新扩容节点生成同样的 Unit 资源池，将同一 Zone 下的租户数据分区均衡到新节点。修改资源池 unit num 的详细操作可参见官网《OceanBase K8s 运维工具》文档 [使用指南/租户管理/修改租户/资源管理](https://www.oceanbase.com/docs/community-ob-operator-doc-1000000000659360) 中 **修改资源池 unit num** 章节。
