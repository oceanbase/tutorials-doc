# 5.1 使用 OCP 进行运维

社区版 OCP 是一个专为 OceanBase 数据库设计的企业级管理平台，它帮助用户轻松管理数据库集群的全生命周期，包括安装、运维、性能监控、配置、升级、删除以及主机的添加和删除等。OCP 还提供了租户管理功能，支持租户创建、结构拓扑显示、性能监控、会话管理和参数管理。此外，其监控告警功能允许用户设定集群、租户和主机的监控规则，并通过 HTTP 或脚本通道发送告警通知。系统管理方面，OCP 允许查看和管理任务，以及自定义参数配置。在安全层面，OCP 支持用户和角色管理，确保数据库的安全访问。通过资源管理功能，管理员可以查看集群的 Unit 分布和资源使用情况。

### OCP 接管 OceanBase 数据库

当 OBD 或 OCP 部署的 OceanBase 集群需要使用新的 OCP 进行管理时，可通过接管功能将 OceanBase 数据库接管到当前 OCP 中，并使用当前 OCP 对新接管的集群继续运维和管理。目前支持接管手动创建、OBD 创建或其它 OCP 创建的 OceanBase 数据库。

### OCP 接管 OBProxy

可通过接管操作将其他 OCP 部署的 OBProxy 服务添加到当前 OCP 中已有的 OBProxy 集群中，并通过当前 OCP 对新组成的 OBProxy 集群继续运维和管理。

适用场景：OCP 部署的 OBProxy 集群。
<!-- 这个适用场景没有看懂，适用于当前环境存在其他 OCP 部署的 OBProxy，还是说当前 OCP 中存在 ODP集群呢 -->
使用 OCP 接管  OBProxy 集群前，需了解如下信息：

* 使用接管功能之前，需要先使用 OCP 部署一个 OBProxy 集群（可以是单节点），需当前 OCP 中存在 OBProxy 集群才可接管其它 OBProxy 集群。
  <!-- 如果适用场景里说的是 当前 OCP 中存在 ODP 集群，那这条注意事项就不需要了，和适用场景重复 -->

* 仅支持接管 OCP 部署的 OBProxy 服务，OBD 部署的 OBProxy 暂不支持接管。

* 接管过程会检查主机中 OBProxy 进程，因此需要待接管 OBProxy 的服务状态是正常的，并且保证主机上有且仅有一个 OBProxy 进程。

* 当前 OCP 中已有的 OBProxy 集群需要先关联待接管 OBProxy 服务所要连接的 OceanBase 集群，即 OBProxy 集群可连接的 OceanBase 集群需要包含待接管的 OBProxy 可连接的 OceanBase 集群。

* 待接管的 OBProxy 服务版本不能和当前 OBProxy 集群版本差太大，建议保证大版本统一，例如 V4.1.x，第三位的 x 版本号可以不一致。

* 接管成功后建议在原 OCP 上迁出已被新 OCP 接管的 OBProxy 集群。

## OCP 迁出集群

迁出集群指的是将当前 OCP 管理的 OceanBase 集群或 OBProxy 集群从平台的管理范围内移除，移除后的集群可被其他 OCP 服务接管并管理。

### OCP 迁出 OceanBase 集群

当需要使用新的 OCP 管理原 OCP 管理的 OceanBase 集群时，可在原 OCP 中将对应的 OceanBase 集群迁出。将 OCP 管理 OceanBase 集群迁出管理，不会影响集群的业务和业务数据，也可重新被 OCP 接管并管理。

使用 OCP 迁出 OceanBase 数据库前，需了解如下信息：

* 社区版 OCP 自 4.2.2 版本起支持该功能。

* 运维或升级状态下的 OceanBase 集群不支持迁出，即集群需处于 `STOPPED`、`RUNNING` 或 `UNAVAILABLE` 状态（通过 xxx 查看）时不支持迁出。
  <!-- 补充如何查看集群状态 -->

* 迁出集群后，如果被迁出的 OceanBase 集群主机没有其他服务，建议删除对应主机。
  <!-- 补充删除主机的操作链接 -->

具体操作可以参看文档 [迁出 OceanBase](https://www.oceanbase.com/docs/common-ocp-1000000000585002)。

### OCP 迁出 OBProxy 集群

通过 OCP 迁出 OceanBase 集群后，如需搭配迁出 OBProxy 集群，OCP 也支持将 OCP 管理 OBProxy 集群迁出管理，并且不会影响 OBProxy 集群的业务，OBProxy 集群也可重新被 OCP 接管并管理。

使用 OCP 迁出 OBProxy 集群前，需了解如下信息：

* 社区版 OCP 自 4.2.2 版本起支持该功能。

* 运维或升级状态下的 OceanBase 集群不支持迁出，即集群需处于 RUNNING 状态。

具体操作可以参看文档 [迁出 OBProxy](https://www.oceanbase.com/docs/common-ocp-1000000000584804)和 [运维实践 - 迁出 OBProxy](https://www.oceanbase.com/docs/common-ocp-1000000000630672)。

## OCP 数据备份和恢复

备份恢复是 OceanBase 数据库常用的容灾方案之一，通过 NFS、OSS、COS 备份介质实现租户级别或集群级别策略的远程物理备份，以保障数据的安全。同时也可以通过恢复功能从备份数据中恢复数据。

### 备份介质

数据备份前需要先部署备份介质，目前 OceanBase 集群支持 NFS、OSS、COS 三种备份介质，建议使用 OSS 作为备份的目的端，OSS 作为无状态的对象存储，相较有状态的 NFS4 具有更高的稳定性。如需要使用 NFS 作为备份目的端，建议使用专用的 NFS 硬件设备。

部署备份介质前需了解如下信息：

* NFS 介质需要使用 NFS4.1 或之后版本，NFS3 版本稳定性较差。

* 多节点集群环境必须使用备份介质，否则无法进行数据备份；单机测试环境可以本地备份，但存在安全风险。

* 使用 OSS 备份介质需保证 OceanBase 数据库为 4.1.0 版本，使用 COS 备份介质需保证 OceanBase 数据库为 V4.2.1 或之后版本。
  <!-- OSS 只能 4.1.0 可以用么，之后版本也不行？ -->

* 如果使用 NFS 备份介质，OceanBase 集群每个节点均需要部署 NFS 客户端。

* 尤其注意 NFS 客户端和服务端目录访问权限问题，OceanBase 数据库进程用户需要有读写权限。

此操作为物理备份前必备过程，实际操作可以参看文档[部署 NFS](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000000507682)。

### 数据备份

部署备份介质后，即可在 OCP 界面侧边栏选择 **备份恢复** -> **备份**，新建租户级别或者集群级别的备份策略，其中集群级别的备份策略也是租户粒度的所有业务租户的数据备份。新建备份策略后，不会立即触发备份，默认每天凌晨四点触发，也可以手动触发 `立即备份` 功能。

### 数据恢复

OceanBase 数据库支持租户级别的恢复，恢复是基于已有数据的备份重建新租户的过程。恢复过程包括租户系统表和用户表的 Restore 和 Recover 过程。Restore 是将恢复需要的基线数据恢复到目标租户的 OBServer 节点，Recover 是将基线数据备份过程中产生的增量数据日志恢复到 OBServer 节点中。

OceanBase 数据库的物理恢复架构如下图所示。

![17110272312884.jpg](10.o-m-by-ocp-02)

使用 OCP 进行数据恢复前，需了解如下信息：

* 建议数据恢复的目标集群和源集群数据库版本保持一致。

* OceanBase 数据库当前仅支持将低版本的备份数据恢复到同版本或高版本中，但不支持 OceanBase 数据库 3.x 的备份数据恢复到 OceanBase 数据库 4.x 版本。

* 对于特殊版本如 OceanBase 数据库 4.0.x 版本的备份数据也不支持恢复到 OceanBase 数据库 4.1.x 及之后版本。

* 恢复界面中如果 **可恢复时间** 显示为空或者无法选择 **源租户** 信息，可能是因为 OBD 部署的 OceanBase 数据库安装目录的 `bin` 目录下缺少 `ob_admin` 文件（可官网下载页面下载 OceanBase Utils 包解压获取）。

## OCP 升级集群

使用 OCP 管理的集群主要有 OceanBase 集群和 OBProxy 集群，升级所管理的集群时可按以下三个流程进行。

### 升级 OCP

使用 OCP 升级集群之前需要先确认是否需要升级 OCP。可以通过版本号进行确认，OCP 服务在 V4.2.0 开始和 OceanBase 数据库版本进行对齐，需要确保 OCP 服务版本和要升级的集群目标版本保持一致即可。同时也可以通过 OCP 发布版本的 Release Notes 确认版本升级依赖关系。
<!-- 是要和要升级的目标版本保持一致对不 -->

目前 OCP 主要有两种部署方式，通过 OBD 图形化界面部署 OCP 和通过容器部署 OCP，不同方式部署的 OCP 的升级操作也不一样。

[使用 OBD 升级 OCP](https://www.oceanbase.com/docs/common-ocp-1000000000584958)

使用 OBD 升级 OCP 前，需了解如下信息：

* 仅支持 OCP V4.0.3 及之后版本通过该方式进行升级。

* OCP 节点需要安装 JAVA 环境，目前仅支持 JDK1.8 版本，并要求构建版本号至少需为 161。

* OBD 可升级容器部署的 OCP，升级过程中会关闭该容器，并重新使用 RPM 包部署新的 OCP 服务，不再使用容器方式管理该 OCP。

* 获取到需要升级的 OCP 软件包后，推荐使用 `obd web upgrade` 命令图形化界面升级方式。
  <!-- 两种方法中更推荐使用 OBD 升级对不 -->

[使用容器升级 OCP](https://www.oceanbase.com/docs/common-ocp-1000000000584960)

该方法仅适用于升级通过容器部署的 OCP，升级前需了解如下信息：

* 升级前需要先停止容器。

* 新启动的 OCP 容器名不能和升级前的容器名相同，否则会启动失败。

### 升级 OceanBase 集群

使用 OCP 升级 OceanBase 集群前，需了解如下信息：

* 升级集群前，需要上传 3 个 OceanBase 软件包：数据库包（oceanbase-ce-\*.rpm）、数据库依赖包（oceanbase-ce-libs-\*.rpm）、数据库工具集成包（oceanbase-ce-utils-\*.rpm）。

* 升级集群前，建议确认下对应版本 [升级说明](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000000247670)。

* 升级集群前，集群状态需要保证健康正常的，不建议对 `运维中` 状态下的集群进行升级。

### 升级 OBProxy 集群

   适用场景：版本缺陷修复、版本特性支持、版本配套要求等。

   注意事项：

   1. 升级 OBProxy 集群时，会同时升级集群中所有 OBProxy，因此该 OBProxy 集群将停止对外服务。如当前 OBProxy 集群已承载业务，建议根据当前配置的负载均衡，分批升级集群中的 OBProxy 服务。
   2. 对存在多个 CPU 架构的 OBProxy 集群进行升级时，若某个 CPU 架构 中缺少所选择的安装包版本时，将无法进行升级。

   具体操作可以参看文档 [升级 OBProxy](https://www.oceanbase.com/docs/common-ocp-1000000000584810)。

## OCP 扩缩容 OceanBase 集群及租户

   OceanBase 有两种添加/缩减节点的场景，横向添加/缩减节点会增加/减少 Zone 的个数，实现控制租户副本个数。纵向添加/缩减节点会增加/减少 OBServer 的个数，实现控制租户资源上限。因此可以对租户进行副本数和资源使用限制进行调整，以满足不同业务场景下对容灾、性能、运维等要求。

### OCP 扩容 OceanBase 集群及租户

   适用场景：拓展机房数量，提供更可靠的高可用能力或业务迁移机房，在几乎不影响业务访问的情况下，将 OceanBase 集群的所有 Server 迁移到其他机房。

   [横向扩容 Zone](https://www.oceanbase.com/docs/common-ocp-1000000000585017)

   添加 Zone 时会在该 Zone 下新增 OBServer 服务，从而增加集群的副本数量，但不能增加集群的资源(CPU、内存、磁盘容量)水平使用上限，例如：数据磁盘存储数据上限不会提升、单 Zone 下的整体资源不会提升。

   适用场景：单机扩容成分布式集群或者少 Zone 集群扩容成 多 Zone 集群提高容灾能力。

   注意事项：

   1. 扩容 Zone 前，需要`软件包管理`中包含 OceanBase 3 个安装包，数据库包(oceanbase-ce-\*.rpm)、数据库依赖包(oceanbase-ce-libs-\*.rpm)、数据库工具集成包(oceanbase-ce-utils-\*.rpm)。
   2. 扩容 Zone 前，需要先添加主机，主机节点建议先进行[服务器初始化](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000000642556)。
   3. 扩容 Zone 前，集群状态需要处于`运行中`。
   4. 扩容 Zone 时，扩容任务失败支持`回滚`，如果回滚失败，不建议对任务进行`跳过`或`设置为成功`，需要联系 OceanBase 技术支持人员协助排查。
   5. 扩容 Zone 完成后，并不会自动为租户添加上副本，需要进入 `租户管理` 点选所需的租户，进行[新增副本](https://www.oceanbase.com/docs/common-ocp-1000000000584889)。
   6. 扩容 Zone 完成后，如果 primary Zone 是顺序优先级策略，不能增加集群计算性能。如果 primary Zone 是随机策略，一般对分区表的性能是有一些影响的，具体需要看业务使用场景。例如：对分区表而言扩容后分区会打散到更多节点，每个节点分区数减少，计算速度提升，但跨了更多个节点数可能增加网络I/O等。

   具体操作可以参看文档 [扩展 OceanBase 集群及租户的高可用](https://www.oceanbase.com/docs/common-ocp-1000000000584776)。

   [扩容租户副本](https://www.oceanbase.com/docs/common-ocp-1000000000584889)

   这里扩容租户有两种场景，扩容租户副本，也可以调整租户[Unit 规格](https://www.oceanbase.com/docs/common-ocp-1000000000584663)，增加租户资源使用上限。

   适用场景：扩容 Zone 后新增副本、调整租户 CPU、内存等资源。

   注意事项：

   1. 新增副本，OceanBase 4.0 ~ 4.2 版本，仅支持全能型副本，即 F 副本。
   2. 新增副本，OceanBase 4.2 及以上版本，支持全能型副本和只读副本，即 F 副本和 R 副本。
   3. 增加 Unit 规格时，建议保持租户的日志盘是租户内存的3~4倍大小。

   具体操作可以参看文档 [扩展 OceanBase 集群及租户的高可用](https://www.oceanbase.com/docs/common-ocp-1000000000584776)。

   [纵向扩容 OBServer](https://www.oceanbase.com/docs/common-ocp-1000000000585024)
   在已有的 Zone 中添加 OBServer 节点，可增加 Zone 的资源(CPU、内存、磁盘容量)使用上限，并提升集群计算能力，例如：1-1-1 架构集群纵向扩容成 2-2-2 架构，单 Zone 下的整体资源会提升，计算能力会提升。

   适用场景：集群性能达到瓶颈、数据存储达到阀值。

   注意事项：

   1. 扩容 OBServer 前，需要先添加主机，主机节点建议先进行[服务器初始化](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000000642556)，虽然 OCP 添加 OBServer 也会对服务器节点做一些初始化动作，建议手动按源集群服务器初始化过程进行一次配置，确保万无一失。
   2. 扩容 OBServer 前，需要`软件包管理`中包含 OceanBase 3 个安装包，数据库包(oceanbase-ce-\*.rpm)、数据库依赖包(oceanbase-ce-libs-\*.rpm)、数据库工具集成包(oceanbase-ce-utils-\*.rpm)。
   3. 扩容 OBServer 前，建议和源集群服务器资源配置保持一致，保证资源的合理利用，降低木桶效应带来的资源浪费。
   4. 扩容 OBServer 前，扩容节点的主机需要和集群硬件架构的主机一致，例如：CPU 架构。
   5. 扩容 OBServer 前，集群状态需要处于`运行中`。
   6. 扩容 OBServer 时，扩容任务失败支持`回滚`，如果回滚失败，不建议对任务进行`跳过`或`设置为成功`，需要联系 OceanBase 技术支持人员协助排查。
   7. 扩容 OBServer 后，租户的数据并不会自动均衡到新节点，需要进入 `租户管理` 点选所需的租户，进行[修改 Unit](https://www.oceanbase.com/docs/common-ocp-1000000000584889)，才会在新扩容节点生成同样的 Unit 资源池，将同一 Zone 下的租户数据分区均衡到新节点。

   具体操作可以参看文档 [扩容 OceanBase 集群及租户](https://www.oceanbase.com/docs/common-ocp-1000000000584780)。
  
   [扩容租户 Unit 数量](https://www.oceanbase.com/docs/common-ocp-1000000000584888)
   这里的扩容租户 Unit 数量主要讲的是通过 增加 Unit 数量，增加租户可使用同 Zone 的下 OBServer 节点数，达到数据分区均衡，缓解单 OBServer 节点上磁盘数据存储压力，增大 Unit 数量的租户，会在新 OBServer 上创建同配置的租户 Unit 资源池，可通过降低该租户资源上限，释放出资源供其他租户扩容资源或创建新租户。

   适用场景：纵向扩容后的 OceanBase 集群。

   注意事项：

   1. OceanBase V4.0 及之后版本，要求租户中每个 Zone 下的 Unit 数量保持一致。例如：集群架构是 2-2-1 或 2-1-1 时，不允许租户的 Unit 设置为 2，即只有 2-2-2 架构下，租户的 Unit 才能设置为 2。
   2. 当普通租户所属集群为 V4.2.0 及以上版本，且租户参数 enable_rebalance 为 false 的情况下，无法修改 Zone 的 Unit 数量。
   3. 扩容租户的 Unit 数量不能大于所在 Zone 内 OBServer 的数量。
   4. 扩容租户 Unit 前，集群与租户需为`运行中`状态。
   5. 租户扩容 Unit 时，扩容任务如果失败了，不推荐进行任务回滚，回滚任务时租户将不会自动缩容回原先规格，也不建议对任务进行`跳过`或`设置为成功`，需要联系 OceanBase 技术支持人员协助排查。

   具体操作可以参看文档 [扩容 OceanBase 集群及租户](https://www.oceanbase.com/docs/common-ocp-1000000000584780)。

### OCP 缩容 OceanBase 集群及租户

   适用场景：缩减租户副本，减小集群规模 或 业务迁移机房，需要先添加新 Zone，再删除旧 Zone。

   [缩容租户副本](https://www.oceanbase.com/docs/common-ocp-1000000000584887)

   这里缩容租户主要指的是减少租户的副本数量。

   适用场景：腾出资源，供其他业务租户使用 或 集群需要做 Zone 缩容。

   注意事项：

   1. 删除副本前，OceanBase 集群、租户必须为`运行中`状态，其他状态不允许进行操作。
   2. 删除副本前，需要确保删除副本后租户的副本能满足多数派。即 3 副本租户最多只能删除 1 个副本。
   3. 删除副本前，建议主动将主副本切走，即修改租户的 [Primary Zone 优先级](https://www.oceanbase.com/docs/common-ocp-1000000000584671)，确保副本删除时不影响业务。

   具体操作可以参看文档 [缩减 OceanBase 集群及租户的高可用](https://www.oceanbase.com/docs/common-ocp-1000000000584781)。

   [横向缩容 Zone](https://www.oceanbase.com/docs/common-ocp-1000000000585015)

   缩容 Zone 时会删除该 Zone 下 OBServer 节点和删除该 Zone ，来减少集群的 Zone 个数，释放出主机节点。

   适用场景：服务器维修 或 降低集群规模等。

   注意事项：

   1. 缩容 Zone 前，集群状态需要处于`运行中`。
   2. 缩容 Zone 前，需要保证 Zone 上已无租户副本，即需要先进行[缩容租户副本](https://www.oceanbase.com/docs/common-ocp-1000000000584887)，可批量删除租户副本。
   3. 缩容 Zone 时，扩容任务失败支持`回滚`，如果回滚失败，不建议对任务进行`跳过`或`设置为成功`，需要联系 OceanBase 技术支持人员协助排查。

   具体操作可以参看文档 [缩减 OceanBase 集群及租户的高可用](https://www.oceanbase.com/docs/common-ocp-1000000000584781)。

   [缩容租户 Unit 数量](https://www.oceanbase.com/docs/common-ocp-1000000000584888)

   这里的缩容租户 Unit 数量主要讲的是通过 减少租户 Unit 数量来减少租户可使用同 Zone 的下 OBServer 节点数，该过程会随机选取同 Zone 下的 OBServer 节点，并将该节点的数据迁移到同 Zone 其他正在使用的 OBServer 节点上，删除缩容节点上的 Unit 资源池，释放资源(CPU、内存等)，因为数据盘和事务日志盘是预占用空间，不会影响该节点磁盘预占用空间大小。

   适用场景：需要缩容 OBServer 节点 或者 腾出集群资源供其他租户使用。

   注意事项：

   1. 缩容租户 Unit 前，集群与租户需为`运行中`状态。
   2. 缩容租户 Unit 前，建议对租户进行`合并`，释放租户正在使用的内存，提高缩容效率。
   3. 缩容租户 Unit 前，需要确保剩下的 OBServer 节点磁盘剩余资源足够支撑缩容租户的数据。
   4. 如果需要缩容到指定 OBServer 节点上，需要进行[手动迁移 Unit](https://www.oceanbase.com/docs/common-ocp-1000000000585027)，注意：需要先关闭租户的`enable_rebalance`资源自动负载参数。
   5. 当 OceanBase 集群为 V4.2.0 及以上版本，且租户参数`enable_rebalance`(默认`true`) 为`false` 的情况下，是无法修改 Unit 数量的。
   6. 在多 Zone 集群场景，OceanBase V4.0.0 及以上时，不支持减少单个 Zone 的 Unit 数量，且副本类型仅支持 全能型副本 类型。即 2-2-2 架构集群或租户，租户只能缩容成 1-1-1 架构，不能缩容成 2-1-1 或 2-2-1 架构。
   7. 缩容租户时，如果任务失败了，不推荐进行任务回滚，也不建议对任务进行`跳过`或`设置为成功`，需要联系 OceanBase 技术支持人员协助排查。

   具体操作可以参看文档 [缩容 OceanBase 集群及租户](https://www.oceanbase.com/docs/common-ocp-1000000000584764)。

   [纵向缩容 OBServer](https://www.oceanbase.com/docs/common-ocp-1000000000585021)
   在已有的 Zone 中删除 OBServer 节点，释放出服务器资源，例如：2-2-2 架构集群纵向缩容成 1-1-1 或 2-1-1 或 2-2-1 架构，建议缩容时尽量在 Zone 中删除相同数量的 OBServer 节点，以保证 Zone 之间的资源均等，即推荐缩容成 N-N-N 集群架构( N 值保持一致)。

   适用场景：腾出服务器资源 或者 服务器维修等。

   注意事项：

   1. 缩容 OBServer 前，集群需为`运行中`状态。
   2. 缩容 OBServer 前，需要确认缩容的 OBServer 节点的租户已经迁移完成`Unit`。
   3. 缩容 OBServer 时，缩容任务如果失败，不建议对任务进行`跳过`或`设置为成功`，需要联系 OceanBase 技术支持人员协助排查。

   具体操作可以参看文档 [缩容 OceanBase 集群及租户](https://www.oceanbase.com/docs/common-ocp-1000000000584764)。

## OCP 替换 OceanBase 节点

   OCP 替换功能主要用于大于等于 3 副本集群中出现故障(服务器无法启动、硬件故障等) OBServer 节点时，或者部署时大于等于 3 副本的集群时参数设置不合理但又不能整体重装解决时，例如：数据磁盘预占用太大，可通过替换操作快速解决节点故障的潜在危险，实现集群的高可用能力、业务的稳定性和运维的高效性。

### 有替换服务器

   适用场景：有空闲的服务器储备，集群节点因外部因素故障短期无法修复等。
   注意事项：

   1. 需要集群当前是可用状态，即通过集群能正常访问租户。
   2. 空闲服务器需要和当前集群硬件架构匹配，且该主机需与原来的主机在同一机房内。
   3. 空闲服务器软硬件资源(CPU、内存、磁盘等)需要大于或等于故障节点，特别是磁盘容量。
   4. 替换服务器前，需要先添加主机，主机节点建议先进行[服务器初始化](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000000642556)。
   5. 替换服务器前，`软件包管理`中需要有 OceanBase、OCP-agent 软件包，且版本需要和源集群保持一致。
   6. 替换服务器时，如果故障节点 OBServer 已经`离线`状态，替换过程中需要按提示选择跳过主机运维操作。
   7. 替换服务器时，替换任务如果失败，不建议对任务进行`跳过`或`设置为成功`，需要联系 OceanBase 技术支持人员协助排查。
   8. 替换服务器后，如果该节点部署有 OBProxy 服务，需要单独为该节点部署或[添加 OBPorxy](https://www.oceanbase.com/docs/common-ocp-1000000000584763)。

   具体操作可以参看文档 [OceanBase 集群主机故障处理](https://www.oceanbase.com/docs/common-ocp-1000000000584785)。

### 无替换服务器

   没有替换的服务器时，但又不能因为服务器存在故障存在隐藏风险，或者集群处于`运维中`状态，影响了 OCP 其他运维管理功能。因此需要消除这种负面影响，但这种方式存在一定的风险，例如：集群不能再容忍其他节点出现故障，或者集群性能降低等。

   适用场景：故障节点 OBServer 服务进程在线，能接受业务性能或集群高可用风险。
   注意事项：

   1. 如果短时间可以维修好服务器故障，可以先调整永久下线时间参数`server_permanent_offline_time`，再停止 OBserver 进程，永久下线时间需要按服务器维修好重新上线时间评估。
   2. 如果短时间无法维修好服务器故障，且集群是多 Zone 多 OBServer 集群，例如：2-2-2架构集群，可以考虑手动迁移 Unit 到同 Zone 其他节点，前提是剩余的 OBServer 节点有足够的资源容纳迁移的 Unit，再删除故障 OBServer 节点。
   3. 如果短时间无法维修好服务器故障，集群是多 Zone 单 OBServer 集群，可以考虑缩容集群方案。

具体操作可以参看文档 [OceanBase 集群主机故障处理](https://www.oceanbase.com/docs/common-ocp-1000000000584785)。
